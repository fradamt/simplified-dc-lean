# Simplex FG Module (DC-fj) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the one fixed FG module `SimplexFG.fj` as pure Lean definitions, and prove its static FG lemmas in `Kit.FG`. The module is DC's FG without SG and grades, with the FJ root rule in place of NJ ("DC-fj"). Each pinned lemma names one `docs/FG-COMPOSITION.md` id, and each pin records its coverage clause by clause.

**Architecture:** There are two new Lake libraries in `lean/available-chain`:
- `AvailableChainSimplexFG` (LM, definitions only): FG rows and blocks, the chain state and transition with no NJ heights, the E1/E2 evidence, the FG signing client with its record guards, the DC-fj store (raw and FG-admitted trees, the live caches, `update_finality` in DC form), the FJ controls, the filtered tree and the FJ frame.
- `AvailableChainKitFG` (L5, proofs): the ported DC certificate lemmas and entry geometry, `fg.accountable.v1`, `fg.uniqueJust.v1`, `fg.finalLock.v1`, the client record safety, the store invariant, the store controls (the frame source of ALFS) and the frame lemmas, provenance, the causal-cap core, `fj.crossingNoFinal.v1`, `fj.inBandLock.v1`, `fj.frameFeasible.v1`, and the `fj.twoChanges.core.v1` result.

Code is PORTED (copied and adapted) from verified-consensus. It is not imported across Lake projects. The module does not import the framework, the engine or any AP. It is FG-only: the AP (for example SA) enters later through the framework interface (FRAMEWORK-DESIGN §7.3).

**Tech Stack:** Lean 4 v4.30.0-rc2 and Mathlib v4.30.0-rc2. Both `available-chain` and `decoupled-consensus/verified-consensus` have `lean-toolchain` = `leanprover/lean4:v4.30.0-rc2`. The build uses Lake and the module system.

## Review Focus

1. **The contest changes both viability and `lo`.** In a contest the root is `F` and `lo = H`, so the band is `{H}`: a block whose only witnesses have height `H−1` leaves `D`. In the uncontested or gap frame of the same blocks, `lo = H−1`. r148 §2 and the spec say that the code must change both viability and below-band eligibility (r148 N12). Eligibility and the walk are AP machinery and are not in this module; the AP obligation is `ap.headReachesLo.v1`. The FG half is `lo` and `D`. Test: Task 6, Step 1, a contested view and the uncontested view of the same blocks, checked on `fjFrame` alone; and Task 7's `fjFrame_lo`, `mem_filteredFrom`, `filteredFrom_reachesLo` and `fjFrame_D_nonempty`.
2. **The store controls are the frame source (ALFS).** ALFS reads the frame controls from the FULL store, as DC's live caches: `F = Σ.F`, `H = Σ.hmax`, `(j, J) = (Σ.h_j, Σ.J)`, and the contest over `Σ.T_F`. The HEAD then filters DC's frozen voter tree with these controls. This replaces the R1 view frame of the archived spec (`fg_frame(Σ, V)`, lines 852–876), where the controls came from the frozen view. The Lean form is `storeControls st` (Task 7), and the CENTRAL lemma is `storeControls_eq_fjControls`: under `StoreInv` and `ViewRootInj` on `st.TF`, `storeControls st = fjControls st.F st.TF`. Thus the controls of ALFS are the controls of the view `Σ.T_F`, and the pure frame lemmas of `fjControls` apply to them. The frozen block set enters only through `filteredFrom` (any block set). Test: Task 7 has a store that violates `StoreInv` (a stale cache) where `storeControls` and `fjControls st.F st.TF` differ, so the invariant is necessary.
3. **Natural-number subtraction in `H−1`.** `Height = ℕ` truncates `H−1` at `H ≤ 1`. Test: Task 6 has `decide` examples on the view `{genesis}` (`H = 1`, `Z = genesis`, `lo = 0`, `D = {genesis}`).
4. **The lex order on `(h_j, J.root)` and the selector.** Ties at one height are broken by root. Two distinct candidates with one key (a root collision) make the DC selector return `none`, so the frame falls back to `(0, genesis)`. Every lemma that reads the selected pair assumes `ViewRootInj`. Test: Task 6 has two blocks `B1a`, `B1b` (roots `⟨1⟩`, `⟨2⟩`), each justifying genesis at height 1 (one pair), and children `childA`, `childB` that justify `B1a` and `B1b` at height 2. The frame's `J` is the height-2 entry with the greater root. Task 6 also has a collision example (two distinct blocks with one root) where the frame falls back.
5. **Acceptance viability is not frame viability.** DC-fj's `viable_tree_from` (used only to accept a new F) keeps DC's `h_max − 1`. The frame uses `lo`. In a contest they differ. Test: Task 7 proves `frameViable ⊆ acceptanceViable` and equality without a contest, and gives a `decide` example of strict inclusion in a contest.
6. **An F move does not keep D.** The registry's formal reading of `fj.twoChanges.core.v1` item 3 (from Astra G02) says that an F move below `m−1` CUTS D at F′. Test: Task 13 has Astra's 4-validator example as `decide` examples: the old D holds genesis, the new D does not.
7. **FG admission.** A block off the current F is in the raw tree only. It does not enter `TF`, does not raise `h_max`, and does not enter a duty view. Test: Task 7 has a `decide` example.
